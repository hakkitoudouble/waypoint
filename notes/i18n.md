# Traduction de l'interface — comment c'est fait, et ce qui casse

L'interface est en **français** ; l'anglais reste la langue source et sert de **clé de
traduction**. Ce fichier explique les décisions, les pièges rencontrés, et la marche à
suivre pour ajouter une langue.

## Le choix : le français est la langue de référence

Le code était déjà écrit en anglais ; réécrire les 200 et quelques libellés en français
dans `app.js` aurait mélangé la langue du code et celle de l'interface, sans rien gagner.
La table `web/i18n.js` porte donc des **clés anglaises** et des **valeurs françaises** :

```js
t("Fit map")        // → "Ajuster la carte"
t("Hide great ones") // → "Masquer les Great Ones"
t("{n} of {total}", { n: 3, total: 5 })   // → "3 sur 5"
```

Trois raisons de garder l'anglais comme clé plutôt qu'un identifiant (`toolbar.fit`) :

* une clé manquante dégrade en **anglais lisible**, jamais en `toolbar.fit` à l'écran ;
* le HTML reste lisible sans ouvrir un fichier de traduction, et une chaîne modifiée se
  voit immédiatement dans le diff ;
* `tools/check_i18n.py` peut prouver que **toute clé existe et que toute entrée sert**.

## Le flux, dans l'ordre

1. `web/index.html` porte le texte **anglais** et des attributs
   `data-i18n`, `data-i18n-title`, `data-i18n-aria-label`, `data-i18n-placeholder`,
   `data-i18n-content`.
2. `web/i18n.js` est chargé **après le markup et avant `app.js`** : il réécrit ces nœuds
   sur place. C'est ce qui fait que la première peinture est déjà en français. Le script
   inline du `<head>` pose la classe `.i18n-pending` (body masqué) pour éviter un
   clignotement anglais ; `i18n.js` la retire, et un minuteur de 900 ms la retire aussi si
   `i18n.js` manquait — la page ne peut pas rester blanche.
3. `app.js` résout les libellés **une fois, au chargement**, en constantes
   (`TYPE_LABEL`, `MEDAL_LABEL`, `FUR_LABEL`, `SORT_LABEL`…) et appelle `t()` partout où
   il construit du texte.
4. Changer de langue écrit `cotw.locale` puis **recharge la page**. Un re-rendu complet
   serait le seul autre choix, et il devrait reconstruire la liste, la carte, les
   panneaux et les constantes : le rechargement est plus honnête et plus court.

## Ce qui n'est pas traduit, volontairement

* **Les noms d'espèces et de réserves** viennent des fichiers de sauvegarde et de
  `/api/reserves`. Ils s'affichent tels que le jeu les écrit (anglais). Les traduire
  demanderait une table de 127 espèces + 19 réserves, et fausserait la correspondance
  avec ce que le joueur voit dans le jeu dans une autre langue.
* **`Great One`** reste en anglais (terme d'usage de la communauté), ainsi que `TR`
  (trophy rating) et `CSV`.
* Les **en-têtes du CSV** restent en anglais : c'est un format lisible par machine, les
  colonnes doivent rester stables.

## Les pièges rencontrés

1. **`t` comme nom de variable.** Le fichier utilisait `var t` comme index de boucle dans
   `defaultFilters`, `activeFilterCount`, `renderHours` et trois `forEach`. Un `var t`
   dans une fonction **masque le traducteur pour toute la fonction** : tout appel `t("…")`
   dans cette portée aurait levé `t is not a function` ou, pire, renvoyé un nombre.
   Renommés en `ti` / `tier` / `zoneType`. Ne pas réintroduire de variable nommée `t`.
2. **Les clés s'écrivent avec les caractères littéraux** (`—`, `…`, `«`, `»`), pas avec des
   échappements `\u2014` : le vérificateur extrait les littéraux du source et les compare
   à la table, une clé échappée ne correspondrait à rien.
3. **`data-i18n` sur un élément qui a des enfants** : `apply()` fait `textContent = …` et
   efface les enfants. Le vérificateur refuse ce cas. Pour un texte à trous (le terme
   recherché dans « Aucune espèce ne correspond à « … » »), `I18N.split(clé, "term")`
   renvoie les deux morceaux et le `<b>` est inséré entre les deux.
4. **PowerShell de cet environnement n'est pas UTF-8.** `Get-Content`/`Set-Content` sont
   passés par la page de code ANSI : `app.js` s'est retrouvé en mojibake + BOM après un
   remplacement de variables. C'est réversible (chaque octet UTF-8 avait été relu en
   cp1252 — vérifié octet par octet), mais la règle est : **éditer avec les outils
   d'édition**, ou avec `[IO.File]` + `UTF8Encoding($false)` explicite.
5. **Le `<title>` et la `<meta name="description">`** se traduisent par attribut
   (`data-i18n` / `data-i18n-content`). Pour la meta, la valeur de l'attribut doit être
   identique au `content` — c'est vérifié, sinon les deux divergent en silence.

## Le rechargement, et les filtres

Puisque changer de langue recharge, tout ce qui vit en mémoire est perdu : c'était
inacceptable pour les filtres (c'est l'interaction principale). `state.filters` est donc
persisté dans `cotw.filters`, en n'écrivant **que les entrées `false`** : une espèce qui
apparaît dans un scan ultérieur arrive cochée. Sont déjà persistés : thème, langue, tri,
heure, mode d'horloge.

Restent perdus à la bascule : le zoom et le déplacement de la carte, l'onglet ouvert.

## Chiffres et dates

* Décimales à la virgule via `num()` (`48,2 kg`), milliers à l'espace fine
  (`4 004`), déjà en place dans `thousands()`.
* Dates via `toLocaleString("fr-FR")` → « scanné 30 oct., 20:44 ».
* Les chiffres restent en chiffres arabes, aucune autre transformation.

## Vérification

```
python tools/check_i18n.py                  # table + markup (18 contrôles)
node work/uiboot/i18n.js                    # unités de i18n.js (33 contrôles)
node work/uiboot/boot.js                    # UI réelle en français (jsdom)
COTW_LOCALE=en node work/uiboot/boot.js     # UI réelle en anglais
COTW_SEED_FILTERS=1 node work/uiboot/boot.js  # restauration d'un filtre sauvegardé
```

`check_i18n.py` évalue `i18n.js` **dans Node** (donc la table doit parser), puis exige :

* toute clé utilisée par `app.js` (`t("…")`, `I18N.split("…")`) existe dans la table ;
* toute clé du `data-i18n*` d'`index.html` existe ;
* aucune entrée de la table n'est inutilisée ;
* chaque valeur conserve exactement les `{placeholders}` de sa clé ;
* aucune valeur française n'est une simple copie de l'anglais (liste blanche : noms
  propres, unités, termes de jeu) ;
* **tout nœud de texte visible d'`index.html` est couvert** par un `data-i18n` (les
  nombres, unités et tirets sont exemptés) — c'est ce qui empêche de recoller du français
  dans le HTML, et `check_ui.py` vérifie en plus qu'aucun accent français n'y traîne ;
* aucun `data-i18n` n'a d'enfants ; aucun attribut `data-i18n-*` inconnu.

`boot.js` vérifie le rendu réel dans les deux langues : `html[lang]`, le libellé de
chaque zone de l'interface, l'absence de **tout** libellé de l'autre langue dans la page,
et le séparateur décimal de la liste. `i18n.js` teste le module seul : recherche,
interpolation, `split()`, réécriture des attributs, persistance, rechargement, stockage
bloqué (`file://`, navigation privée) et clé inconnue.

Enfin, cinq captures Chrome headless (`work/shots/`) servent de contrôle visuel :
`fr-desktop.png`, `en-desktop.png`, `fr-520x900.png` (compact), `fr-tall.png` (tout le
panneau de filtres) et `fr-restored-filters.png` — cette dernière avec un `cotw.filters`
pré-rempli, qui montre « 13/14 » espèces, la ligne décochée et le sexe filtré.

## Ajouter une langue

1. Copier le bloc `fr` de `web/i18n.js`, traduire les valeurs, ajouter la langue à `DICT`,
   à `locales` et à `NAMES`.
2. Étendre `EXPECT` dans `work/uiboot/boot.js` (libellés attendus + libellés interdits).
3. Lancer `python tools/check_i18n.py` : il liste exactement les clés manquantes.
4. Attention aux pluriels : `plural(n, t("animal"), t("animals"))` attend deux formes ;
   une langue à trois formes demanderait de passer par une clé `{n}` dédiée.

## Limites connues

* Deux langues seulement, et les noms d'espèces/réserves restent dans la langue des
  fichiers du jeu.
* Pas de test navigateur dans la suite : `jsdom` ne fait pas de mise en page. Chrome
  headless a servi aux captures, à la main. Conséquence : une régression purement CSS
  (débordement d'un libellé long) ne serait pas attrapée par les tests.
* Le libellé le plus long introduit par le français allonge la barre d'outils de la
  carte d'environ 60 px ; elle est autorisée à passer sur deux lignes (`.map-toolbar {
  flex-wrap: wrap }`) et le fait à partir de ~1250 px de large.
